# v1.2.0 Multi-Signature Policy and Transparency Log

v1.2.0 extends the v1.1.0 trusted policy delivery model with two mechanisms:

1. multi-signature policy authorization; and
2. append-only transparency logging for issued policy records.

## Multi-signature policy

The v1.2.0 envelope contains:

```json
{
  "policy": {"id": "policy-v120", "sequence_no": 1},
  "signature_policy": {
    "version": "v1.2.0",
    "threshold": 2,
    "required_roles": ["controller", "security"]
  },
  "signatures": [
    {"key_id": "controller-key", "algorithm": "Ed25519", "signature": "...", "role": "controller"},
    {"key_id": "security-officer-key", "algorithm": "Ed25519", "signature": "...", "role": "security"}
  ]
}
```

Each signer signs canonical JSON over both the policy body and the signature
policy. Therefore, the threshold and required role set cannot be changed without
invalidating the signatures.

## Rejection reason codes

Typical v1.2.0 multi-signature rejection codes include:

- `MISSING_SIGNATURES`
- `MULTISIG_THRESHOLD_NOT_MET`
- `MULTISIG_REQUIRED_ROLE_MISSING`
- `DUPLICATE_SIGNER`
- `UNKNOWN_SIGNING_KEY`
- `REVOKED_SIGNING_KEY`
- `POLICY_SIGNATURE_INVALID`
- `UNSUPPORTED_SIGNATURE_ALGORITHM`

## Transparency log

The transparency log is a hash-chained JSONL audit log. Each entry records:

- index;
- policy_id;
- sequence_no;
- policy digest;
- previous entry hash;
- entry hash;
- signer key IDs;
- threshold;
- decision and reason code.

This provides a lightweight local append-only audit trail for policy issuance.
A later v1.2.x or v1.3.0 step can replace the local JSONL store with a remote
transparency service.

## Validation

Run:

```bash
python -m pytest -q
python examples/multisig_transparency_demo.py
```

Expected demo behavior:

- a 2-of-2 policy is accepted;
- ACK contains `signature_mode=multi-signature`;
- a transparency log entry is appended;
- hash-chain verification returns `OK`.

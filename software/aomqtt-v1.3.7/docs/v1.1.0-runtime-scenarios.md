# v1.1.0 Runtime Trust Scenarios

This document describes the v1.1.0 scenario runner for validating trusted policy delivery and key lifecycle hardening.

## Purpose

The scenario runner provides a reproducible smoke test for the v1.1.0 runtime path:

1. accepted signed policy
2. unknown signing key rejection
3. revoked signing key rejection
4. invalid policy signature rejection
5. unsafe policy rejection by the Policy Guard layer

These scenarios are intentionally small and deterministic. They are designed to verify the behavior before connecting the processor to a live MQTT Control Receiver.

## Run

```bash
RUN_ID=run-v110-trust-scenarios-001 ./experiments/run_v110_trust_scenarios.sh
```

or:

```bash
python experiments/run_v110_trust_scenarios.py \
  --run-id run-v110-trust-scenarios-001 \
  --results-root results \
  --client-id subscriber-v110-scenario
```

## Output

The runner writes the following files under `results/<run_id>/`:

```text
control_ack_summary.csv
control_ack_summary.json
controller_anomaly_report.csv
controller_anomaly_report.json
v110_trust_scenario_summary.json
```

## Expected result

The expected summary is:

```text
total=5
accepted=1
rejected=4
```

Expected reason codes:

```text
OK
UNKNOWN_SIGNING_KEY
REVOKED_SIGNING_KEY
POLICY_SIGNATURE_INVALID
PADDING_TOO_LARGE
```

## Relationship to live Control Receiver integration

This runner does not require a broker. It exercises the same `TrustedControlPolicyProcessor` that the live Control Receiver should call from its MQTT control callback:

```python
result = processor.process_payload(msg.payload)
publish_control_ack(result.ack)

if not result.accepted:
    return

apply_policy(result.policy)
```

After these scenarios pass, the next step is to bind this processor to the existing v1.0.2 Control Receiver callback and publish the final ACK on the existing ACK topic.

# v1.1.0 Control Receiver Trust Bridge

This document describes how to connect the v1.1.0 Policy Trust layer to the existing MQTT Control Receiver without breaking the v1.0.2 Policy Guard.

## Integration pattern

Call `verify_control_policy_payload()` immediately after receiving the raw MQTT control-policy payload and before constructing the concrete `ControlPolicyMessage`.

```python
from aomqtt.control_policy_trust import verify_control_policy_payload

result = verify_control_policy_payload(
    msg.payload,
    trusted_public_keys=trusted_public_keys,
    krl=current_krl,
    client_id=client_id,
)

publish_control_ack(result.ack)

if not result.accepted:
    return

# Existing v1.0.2 path starts here.
control_policy = ControlPolicyMessage.from_dict(result.policy)
policy_guard.validate(control_policy)
apply_policy(control_policy)
```

## Strict and transitional modes

By default, unsigned legacy policies are rejected with `MISSING_SIGNING_KEY`.

For staged migration, a receiver can temporarily call:

```python
verify_control_policy_payload(..., require_signature=False)
```

In that mode, legacy unsigned policies are accepted with reason code `LEGACY_UNSIGNED_POLICY`. This should be used only for transition testing, not as the final v1.1.0 security setting.

## Rejection reason codes added by this bridge

- `INVALID_CONTROL_POLICY_JSON`
- `MISSING_SIGNING_KEY`
- `UNKNOWN_SIGNING_KEY`
- `REVOKED_SIGNING_KEY`
- `UNSUPPORTED_SIGNATURE_ALGORITHM`
- `MISSING_SIGNATURE`
- `POLICY_SIGNATURE_INVALID`

The generated ACK keeps the fields needed by Controller-side analysis:

```json
{
  "client_id": "subscriber-1",
  "policy_id": "policy-v110-demo",
  "sequence_no": 1,
  "status": "accepted|rejected",
  "reason_code": "OK|...",
  "signer_key_id": "controller-key-2026-001",
  "signature_algorithm": "Ed25519",
  "signing_method": "local|remote|mock-kms|..."
}
```

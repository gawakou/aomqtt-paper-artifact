# AOMQTT v1.0.0 Result Format

This document defines the standard evaluation result format for AOMQTT Client SDK v1.0.0.

The purpose of this format is to make AOMQTT experiments reproducible, analyzable, and suitable for research papers.

## 1. Design Goals

The v1.0.0 result format is designed to satisfy the following goals:

- each experiment run has a unique `run_id`;
- all raw logs are preserved;
- derived summaries are separated from raw logs;
- paper-ready assets are separated from intermediate outputs;
- controller-side analysis results are exported in both CSV and JSON formats;
- experiment configuration and metadata are preserved;
- results can be regenerated and compared across runs.

## 2. Top-Level Result Directory

All evaluation results must be saved under:

```text
results/<run_id>/
```

Example:

```text
results/run-v100-final/
```

The `run_id` should be explicitly provided by the user or experiment script.

Recommended examples:

```text
run-v100-static
run-v100-observation
run-v100-rejected
run-v100-final
```

## 3. Standard Directory Structure

The standard v1.0.0 result directory structure is:

```text
results/<run_id>/
├── config/
│   └── experiment_config.yaml
├── raw/
│   ├── publisher_metrics.csv
│   ├── subscriber_metrics.csv
│   ├── controller_ack_log.csv
│   ├── controller_status_log.csv
│   └── controller_deployment_events.csv
├── derived/
│   ├── deployment_summary.csv
│   ├── deployment_summary.json
│   ├── ack_status_summary.csv
│   ├── reason_code_summary.csv
│   └── policy_comparison_summary.csv
├── paper/
│   ├── tables/
│   │   ├── table_policy_comparison.csv
│   │   ├── table_ack_status_summary.csv
│   │   └── table_reason_code_summary.csv
│   └── figures/
│       ├── fig_ack_status_breakdown.png
│       ├── fig_policy_result_comparison.png
│       └── fig_reason_code_breakdown.png
└── manifest.json
```

## 4. Directory Roles

### 4.1 `config/`

The `config/` directory stores experiment configuration files.

Required file:

```text
config/experiment_config.yaml
```

This file should describe:

- experiment ID;
- run ID;
- scenario name;
- broker settings;
- topic settings;
- tokenization mode;
- padding policy;
- rotation settings;
- control-policy settings;
- expected output files.

### 4.2 `raw/`

The `raw/` directory stores raw logs generated by publishers, subscribers, and controllers.

Raw logs should not be manually edited.

Expected files:

```text
raw/publisher_metrics.csv
raw/subscriber_metrics.csv
raw/controller_ack_log.csv
raw/controller_status_log.csv
raw/controller_deployment_events.csv
```

### 4.3 `derived/`

The `derived/` directory stores aggregated and normalized analysis outputs.

Expected files:

```text
derived/deployment_summary.csv
derived/deployment_summary.json
derived/ack_status_summary.csv
derived/reason_code_summary.csv
derived/policy_comparison_summary.csv
```

The files in `derived/` should be reproducible from files in `raw/` and `config/`.

### 4.4 `paper/`

The `paper/` directory stores paper-ready tables and figures.

Expected subdirectories:

```text
paper/tables/
paper/figures/
```

Files in this directory should be generated by scripts under `scripts/`.

### 4.5 `manifest.json`

The `manifest.json` file stores run-level metadata.

It should allow users to identify what was executed and where the outputs are stored.

## 5. Manifest Format

The recommended `manifest.json` format is:

```json
{
  "schema_version": 1,
  "project": "AOMQTT Client SDK",
  "version": "v1.0.0",
  "experiment_id": "exp-v100-final",
  "run_id": "run-v100-final",
  "created_at": "2026-06-04T00:00:00+09:00",
  "scenarios": [
    "static_policy",
    "observation_policy",
    "rejected_policy_feedback"
  ],
  "outputs": {
    "config": "config/",
    "raw": "raw/",
    "derived": "derived/",
    "paper": "paper/"
  }
}
```

Required fields:

| Field | Description |
|---|---|
| `schema_version` | Result format schema version |
| `project` | Project name |
| `version` | AOMQTT version |
| `experiment_id` | Experiment identifier |
| `run_id` | Run identifier |
| `created_at` | Creation timestamp |
| `scenarios` | List of executed scenarios |
| `outputs` | Output directory mapping |

## 6. Raw CSV Schemas

### 6.1 Publisher Metrics

Recommended file:

```text
raw/publisher_metrics.csv
```

Recommended columns:

| Column | Description |
|---|---|
| `timestamp` | Event timestamp |
| `client_id` | Publisher client ID |
| `topic` | Original topic or logical topic |
| `protected_topic` | Protected MQTT topic |
| `policy_id` | Applied policy ID |
| `sequence_no` | Message sequence number |
| `qos` | MQTT QoS |
| `success` | Publish success flag |
| `publish_complete_ms` | Publish completion latency in milliseconds |
| `payload_bytes` | Original payload size |
| `encrypted_bytes` | Encrypted payload size |
| `padding_added_bytes` | Added padding size |
| `token_mode` | Topic tokenization mode |
| `rotation_epoch` | Token rotation epoch if available |

### 6.2 Subscriber Metrics

Recommended file:

```text
raw/subscriber_metrics.csv
```

Recommended columns:

| Column | Description |
|---|---|
| `timestamp` | Event timestamp |
| `client_id` | Subscriber client ID |
| `topic` | Original topic or logical topic |
| `protected_topic` | Protected MQTT topic |
| `policy_id` | Applied policy ID |
| `sequence_no` | Message sequence number |
| `received` | Receive flag |
| `duplicate` | Duplicate message flag |
| `decrypt_success` | Payload decryption success flag |
| `delivery_latency_ms` | Delivery latency if available |
| `token_mode` | Topic tokenization mode |
| `rotation_epoch` | Token rotation epoch if available |

### 6.3 Controller ACK Log

Recommended file:

```text
raw/controller_ack_log.csv
```

Recommended columns:

| Column | Description |
|---|---|
| `timestamp` | ACK timestamp |
| `group_id` | Control group ID |
| `client_id` | Client ID |
| `policy_id` | Policy ID |
| `sequence_no` | Policy sequence number |
| `ack_status` | ACK status |
| `reason_code` | Reason code |
| `message` | Human-readable message |
| `raw_payload_available` | Whether raw policy payload was available |

Typical `ack_status` values:

```text
accepted
rejected
expired
invalid_signature
replay_detected
unknown
```

Typical `reason_code` values:

```text
ok
invalid_policy
expired_policy
invalid_signature
replay_detected
padding_limit_exceeded
unknown_key_id
parse_error
unknown
```

### 6.4 Controller Status Log

Recommended file:

```text
raw/controller_status_log.csv
```

Recommended columns:

| Column | Description |
|---|---|
| `timestamp` | Status timestamp |
| `group_id` | Control group ID |
| `client_id` | Client ID |
| `policy_id` | Policy ID |
| `sequence_no` | Policy sequence number |
| `apply_status` | Application status |
| `reason_code` | Reason code |
| `message` | Human-readable message |

Typical `apply_status` values:

```text
applied
failed
timeout
unknown
```

### 6.5 Controller Deployment Events

Recommended file:

```text
raw/controller_deployment_events.csv
```

Recommended columns:

| Column | Description |
|---|---|
| `timestamp` | Event timestamp |
| `group_id` | Control group ID |
| `policy_id` | Policy ID |
| `sequence_no` | Policy sequence number |
| `event_type` | Deployment event type |
| `target_clients` | Number of target clients |
| `accepted_count` | Number of accepted ACKs |
| `rejected_count` | Number of rejected ACKs |
| `applied_count` | Number of applied statuses |
| `failed_count` | Number of failed statuses |
| `timeout_count` | Number of timeout statuses |

## 8. Paper-Ready Assets

Paper-ready tables should be generated under:

```text
results/<run_id>/paper/tables/
```

Expected tables:

```text
table_policy_comparison.csv
table_ack_status_summary.csv
table_reason_code_summary.csv
```

Paper-ready figures should be generated under:

```text
results/<run_id>/paper/figures/
```

Expected figures:

```text
fig_ack_status_breakdown.png
fig_policy_result_comparison.png
fig_reason_code_breakdown.png
```

## 9. Naming Rules

### 9.1 Run ID

Recommended format:

```text
run-v100-<scenario-or-purpose>
```

Examples:

```text
run-v100-static
run-v100-observation
run-v100-rejected
run-v100-final
```

### 9.2 Experiment ID

Recommended format:

```text
exp-v100-<scenario-or-purpose>
```

Examples:

```text
exp-v100-static
exp-v100-observation
exp-v100-rejected
exp-v100-final
```

### 9.3 Scenario Names

Recommended scenario names:

```text
static_policy
observation_policy
rejected_policy_feedback
```

## 10. Reproducibility Requirements

For each run, the following information should be preserved:

- AOMQTT version;
- Git commit hash if available;
- run ID;
- experiment ID;
- scenario name;
- experiment configuration;
- raw metrics;
- derived summaries;
- paper-ready outputs.

Recommended command to record Git commit hash:

```bash
git rev-parse HEAD
```

## 11. Validation Commands

After running an experiment, validate the result structure.

```bash
find results/run-v100-final -maxdepth 3 -type f | sort
```

Check required directories.

```bash
test -d results/run-v100-final/config
test -d results/run-v100-final/raw
test -d results/run-v100-final/derived
test -d results/run-v100-final/paper
test -d results/run-v100-final/paper/tables
test -d results/run-v100-final/paper/figures
```

Check required files.

```bash
test -f results/run-v100-final/manifest.json
test -f results/run-v100-final/derived/deployment_summary.csv
test -f results/run-v100-final/derived/deployment_summary.json
```

## 12. Git Policy for Results

Generated results should not be committed by default.

Recommended `.gitignore` policy:

```text
results/*
!results/.gitkeep
```

This allows the repository to keep the `results/` directory while excluding generated experiment outputs.

## 13. v1.0.0 Result Format Completion Criteria

The result format is considered finalized when:

- all experiment scripts save results under `results/<run_id>/`;
- raw logs are saved under `raw/`;
- derived summaries are saved under `derived/`;
- paper-ready assets are saved under `paper/`;
- `manifest.json` is generated;
- controller-side summaries are exported in CSV and JSON;
- paper-ready tables and figures can be generated from derived summaries.
